# Two-Factor Authentication (TOTP)

## Status

The backend now enables Better Auth's built-in `twoFactor` plugin in
[Auth/auth.js](../app/monitoring-backend/Auth/auth.js).

The implementation supports:

- TOTP authenticator applications such as Google Authenticator, Microsoft
  Authenticator, Authy, and 1Password.
- QR-code provisioning through a standard `otpauth://` URI.
- Six-digit rotating codes generated by the authenticator application.
- Backup recovery codes.
- Trusted-device and two-factor challenge cookies.
- Account lockout after repeated failed two-factor attempts using Better Auth's
  default protection.

The TOTP issuer is configured as `Monitoring Backend`.

## Requirements

The user must first have an email/password account and an active Better Auth
session. Every Postman request with a JSON body must include:

```http
Content-Type: application/json
Origin: http://localhost:5173
```

Keep Postman's cookie jar enabled. Two-factor setup and verification depend on
the Better Auth session and challenge cookies.

## Enable TOTP

### 1. Enable TOTP for the signed-in user

```http
POST http://localhost:3000/api/auth/two-factor/enable
```

```json
{
  "password": "Password123!",
  "method": "totp"
}
```

The response contains a `totpURI` and one-time `backupCodes`:

```json
{
  "method": "totp",
  "totpURI": "otpauth://totp/Monitoring%20Backend%3Atest%40example.com?...",
  "backupCodes": [
    "backup-code-1",
    "backup-code-2"
  ]
}
```

The password is required because the account has an email/password credential.
The `password` field is not needed for passwordless accounts when the plugin is
configured to allow passwordless setup.

### 2. Scan the QR code

The backend returns the `totpURI`, not a rendered image. Convert the URI into a
QR code in the frontend or display it with a QR-code component. Scan it with
the user's authenticator application.

The authenticator application then generates a new time-based code periodically
(normally every 30 seconds).

### 3. Verify the first code

Read the current six-digit code from the authenticator application and call:

```http
POST http://localhost:3000/api/auth/two-factor/verify-totp
```

```json
{
  "code": "123456"
}
```

After successful verification, `twoFactorEnabled` becomes `true`. Store the
backup codes securely; they are recovery credentials and should not be logged
or returned again unnecessarily.

## Two-factor sign-in flow

### 1. Sign in normally

```http
POST http://localhost:3000/api/auth/sign-in/email
```

```json
{
  "email": "test@example.com",
  "password": "Password123!"
}
```

If two-factor authentication is enabled, Better Auth returns a two-factor
challenge instead of completing the normal authenticated session. Keep the
two-factor challenge cookie in Postman.

### 2. Complete the TOTP challenge

```http
POST http://localhost:3000/api/auth/two-factor/verify-totp
```

```json
{
  "code": "123456",
  "trustDevice": false
}
```

If verification succeeds, Better Auth creates the authenticated session cookie.
Set `trustDevice` to `true` only on a device that should skip future challenges
for the configured trusted-device period.

## Backup-code sign-in

Use a backup code if the authenticator application is unavailable:

```http
POST http://localhost:3000/api/auth/two-factor/verify-backup-code
```

```json
{
  "code": "backup-code-1",
  "trustDevice": false
}
```

Backup codes are single-use.

## Manage TOTP

### Get a new TOTP URI

```http
POST http://localhost:3000/api/auth/two-factor/get-totp-uri
```

```json
{
  "password": "Password123!"
}
```

### Generate replacement backup codes

```http
POST http://localhost:3000/api/auth/two-factor/generate-backup-codes
```

```json
{
  "password": "Password123!"
}
```

The returned backup codes replace the previous set. Store the new set safely.

### Disable TOTP

```http
POST http://localhost:3000/api/auth/two-factor/disable
```

```json
{
  "password": "Password123!"
}
```

## Two-factor endpoints enabled

All routes are relative to `http://localhost:3000/api/auth`:

| Method | Route | Purpose |
|---|---|---|
| `POST` | `/two-factor/enable` | Start TOTP enrollment and return the `totpURI` and backup codes |
| `POST` | `/two-factor/verify-totp` | Verify enrollment or complete a TOTP sign-in challenge |
| `POST` | `/two-factor/verify-backup-code` | Complete a challenge with a backup code |
| `POST` | `/two-factor/disable` | Disable TOTP for the current user |
| `POST` | `/two-factor/get-totp-uri` | Return the user's current TOTP provisioning URI |
| `POST` | `/two-factor/generate-backup-codes` | Replace the user's backup codes |
| `POST` | `/two-factor/verify-otp` | OTP verification route; not configured by this project |
| `POST` | `/two-factor/send-otp` | OTP delivery route; not configured by this project |

This project uses TOTP. Email/SMS OTP is not configured because no OTP delivery
provider has been added.

## Security notes

- Never commit `BETTER_AUTH_SECRET`.
- Never store TOTP secrets or backup codes in application logs.
- Treat backup codes like passwords.
- Require HTTPS in non-local environments.
- Use a production-specific issuer and secrets.
- Keep CSRF protection enabled and send a trusted `Origin` header.
- Test recovery procedures before enforcing two-factor authentication for all
  administrators.
